# 成长系统领域模型

| 项目 | 内容 |
|---|---|
| 版本 | 1.0 |
| 冻结日期 | 2026-11-20 |
| 适用版本 | P0 简化个人成长系统 |
| 状态 | 已冻结，后续变更必须新增 ADR 并说明迁移影响 |

## 1. 产品目标

系统围绕一条可验证的成长闭环工作：

```text
身份 → 能力树 → 阶段成果 → 任务 → 时间块 / 学习会话 → 证据 → 复盘
```

四个一级模块分别回答：

| 模块 | 问题 | 主要对象 |
|---|---|---|
| 今天 | 现在做什么？什么时候做？ | 任务、时间块 |
| 路线 | 我要成为谁？需要掌握什么？下一项可验证成果是什么？ | 身份、能力、阶段成果、S 型时间线 |
| 学习 | 我如何学习，并留下什么证据？ | 学习会话、学习记录、证据 |
| 复盘 | 哪些有效，下一步如何调整？ | 日/周/月复盘、调整 |

## 2. 核心实体

### 2.1 Identity｜身份

身份是长期成长的根节点，回答“我想成为怎样的人”。

每个身份至少包含：

```text
Identity
├── name
├── statement
├── status
└── archivedAt
```

规则：

- 身份是能力树的根，不要求用户先创建愿景或方向。
- 愿景是身份的一句话描述，落实为 `statement`，不新增独立必经实体。
- 一个用户可以有多个身份。
- 删除使用归档，不做物理删除。
- P0 不提供身份评分、身份冲突度、人格画像等复杂能力。

### 2.2 Competency｜能力

能力是身份下的多级树节点，回答“为了成为这样的人，我需要掌握什么”。

```text
Competency
├── identityId
├── parentId
├── name
├── currentLevel
├── targetLevel
├── weight
├── description
└── archivedAt
```

规则：

- 根能力的 `parentId = null`，且必须归属一个身份。
- 子能力必须和父能力属于同一身份。
- 能力层级不设固定上限，但 P0 推荐不超过 5 层。
- 父能力汇总子能力；P0 只允许叶子能力挂阶段成果。
- 当前等级与目标等级使用 `L0`–`L5`。
- 任务完成只代表过程推进，不自动提升能力等级。
- 能力等级必须由证据支持，并由用户确认后更新。

### 2.3 Vision 与 Direction 的定位

`Vision` 和 `Direction` 保留为旧数据兼容层，不再作为新用户的必经建模步骤。

- 愿景：降级为身份描述 `Identity.statement`。
- 方向：降级为能力分组标签或旧数据分组，不起身份与能力之间的必经层作用。
- 新页面不得要求用户先创建愿景或发展方向，才能创建身份和能力。
- 旧数据迁移时保留原始记录，不自动推断和覆盖用户语义。

### 2.4 StageOutcome｜阶段成果

阶段成果连接长期能力与具体行动，回答“在某个阶段，我要做出什么可验证的结果”。

为降低迁移成本，P0 复用现有 `Goal` 实体，界面统一称为“阶段成果”。`Milestone` 作为旧数据兼容对象保留，新页面不再创建独立里程碑。

```text
StageOutcome (Goal)
├── competencyId
├── title
├── successCriteria
├── startDate
├── dueDate
├── status
└── archivedAt
```

规则：

- 一个阶段成果必须属于一个叶子能力。
- 一个阶段成果必须写清验收标准。
- 截止日期允许为空，但空日期会在 S 型时间线中进入“未排期”。
- 一个阶段成果可以有多个任务。
- P0 的阶段成果不使用人工进度作为默认值，进度由任务估算时长推导。
- 阶段成果完成后，是否提升能力等级仍由证据和用户确认决定。

### 2.5 Task｜任务

任务是可执行动作，回答“具体要做什么”。

```text
Task
├── stageOutcomeId
├── title
├── completionCriteria
├── scheduledDate
├── dueDate
├── estimatedDuration
├── status
└── completedAt
```

规则：

- P0 新任务必须属于一个阶段成果。
- 任务可安排到某一天，也可以暂时保持未安排。
- 一个任务可以有多个时间块。
- 任务完成状态以 `Task.status` 为唯一事实来源。
- 任务完成后可由用户主动保存证据；不得仅因“完成任务”自动提升能力等级。
- 归档任务不进入默认进度和统计。

### 2.6 Block｜时间块

时间块回答“什么时候做”，不是任务本身。P0 复用现有 `Timebox` 实体。

```text
Block (Timebox)
├── taskId
├── plannedStart
├── plannedEnd
├── plannedDuration
├── actualStart
├── actualEnd
├── actualDuration
├── status
└── kind
```

规则：

- `taskId` 可以为空，支持休息、自由专注等独立时间块。
- 一个任务可以有多个时间块。
- 时间块不得替代任务状态。
- 时间块实际时长不直接等同于能力掌握程度。

### 2.7 Session｜学习会话

学习会话回答“怎么学习、执行”。P0 固定四个阶段：

```text
01 Input｜输入
02 Understand｜理解
03 Output｜输出
04 Review｜回顾
```

```text
Session (LearningSession)
├── taskId
├── blockId
├── startedAt
├── endedAt
├── currentStage
├── status
├── intention
├── reflection
└── selfScore
```

规则：

- 学习会话可以关联任务和时间块。
- 四阶段是固定流程，不为每个任务发明新工作流。
- 学习记录关联会话；阶段输出保存在学习记录中。
- 学习时长用于统计投入，不直接决定能力等级。

### 2.8 Evidence｜成果证据

证据回答“我究竟做出了什么、掌握了什么”。

```text
Evidence
├── taskId
├── title
├── description
├── evidenceType
├── fileUrl
├── externalUrl
└── qualityNote
```

证据与能力的关系通过 `CompetencyEvidence` 记录，包含评估等级和评估说明。

规则：

- 来自任务的证据优先记录 `taskId`，能力关系通过任务所属阶段成果派生。
- 没有对应任务、但直接证明某项能力的证据，可建立能力-证据关系。
- P0 不要求一条证据同时绑定多个互相矛盾的任务。
- 能力等级变化必须记录证据、评估等级、评估时间和用户确认结果。

### 2.9 Review｜复盘

复盘回答“哪些有效，下一步如何调整”。

P0 使用“自动统计 + 三个问题 + 三种调整”：

```text
Review
├── reviewType
├── targetDate
├── content
└── status
```

三种调整：

1. 调整日期。
2. 调整范围或优先级。
3. 调整路径或方法。

规则：

- 复盘先展示自动统计，再让用户回答少量问题。
- 复盘结果必须落到至少一个具体调整，避免只写感想。
- 调整通过统一写入服务执行，不由复盘记录直接修改其他表。
- 日、周、月复盘共用一套结构，只改变统计范围与提示问题。

## 3. 实体关系

```text
Identity
└── Competency
    ├── Competency
    │   ├── Competency
    │   │   └── StageOutcome
    │   │       └── Task
    │   │           ├── Block
    │   │           ├── Session
    │   │           │   └── LearningRecord
    │   │           └── Evidence
    │   └── StageOutcome
    └── StageOutcome

Review
└── 读取上述数据并生成调整
```

硬性约束：

1. 根能力必须属于一个身份。
2. 子能力必须与父能力属于同一身份。
3. 阶段成果只能挂在叶子能力上。
4. 阶段成果必须属于一个能力。
5. 新任务必须属于一个阶段成果。
6. 时间块可以没有任务。
7. 学习会话可以没有任务，但如果有任务，必须引用有效任务。
8. 归档对象默认不进入统计。
9. 所有写操作必须经过统一的 Growth Command。
10. 页面不得自行实现进度公式。

## 4. 进度规则

系统只保留以下四级进度，不把任务完成率直接当成能力掌握度。

### 4.1 阶段成果进度

```text
阶段成果进度 = 已完成任务估算时长 / 全部有效任务估算时长
```

- 已取消、已归档任务不参与计算。
- 无任务的阶段成果进度为 0%。
- 没有估算时长的任务按 30 分钟计权。
- 阶段成果状态由进度和用户操作共同决定，不使用独立人工进度覆盖。

### 4.2 叶子能力等级进度

```text
叶子能力等级进度 = currentLevel / targetLevel
```

- 该进度表示等级距离，不代表阶段成果完成率。
- 等级变化由证据和用户确认触发。

### 4.3 父能力进度

```text
父能力进度 = Σ(子能力进度 × weight) / Σweight
```

- 只汇总直接子能力，避免重复统计后代任务。
- 子能力默认权重为 1，可调整。

### 4.4 身份进度

```text
身份进度 = Σ(根能力进度 × weight) / Σweight
```

UI 必须同时区分：

- 能力等级进度：离目标等级还有多远。
- 阶段成果进度：当前阶段做完了多少。

## 5. S 型时间线

S 型时间线是路线数据的派生视图，不建立独立时间线实体。

数据来源：

- 阶段成果 `dueDate`
- 任务 `dueDate`
- 阶段成果状态与任务进度

规则：

- 按日期升序排列。
- 多行蛇形布局。
- 默认折叠。
- 支持按身份、能力、状态筛选。
- 点击阶段成果节点打开详情抽屉。
- 没有日期的阶段成果进入“未排期”。
- 时间线不是独立规划系统，不维护新的计划副本。

## 6. 非目标

P0 明确不实现：

- 云端同步与账号系统。
- AI 自动修改数据。
- 完整 Fogg 行为模型。
- 间隔复习算法重做。
- 多身份能力共享。
- 复杂能力评分。
- 独立时间线数据库。
- 第二套 Growth OS 项目或第二套长期并行数据库。

## 7. 领域规则变更流程

任何影响以下内容的变更，必须先新增 `docs/architecture/decisions/ADR-*.md`：

- 核心实体关系。
- 进度公式。
- 能力等级更新方式。
- 阶段成果与任务的归属规则。
- 数据库迁移或删除旧表。

变更必须同时更新本文件、数据字典、迁移计划、当前情况台账和验收用例。
